# Github PR

> 말머리는 `CLAUDE.md` `5. Label · 말머리 · 브랜치` 표, 기준 브랜치·병합 방식·팀 구성은 `Docs/TechSpec.md`를 쓴다.
> Unity MCP가 켬이면 `Docs/Claude/UnityMCP.md` `3. 검증 등급`에 따라 PR 직전에 콘솔을 다시 조회한다.

## 1. 정보 수집

- 연결 Issue 번호와 Label을 `gh issue view`로 확인한다. 모르면 묻는다.
- 원격 반영 상태 : `git rev-parse --abbrev-ref @{u}`가 실패하면 `git push -u origin <브랜치>`를, `git status -sb`에 ahead가 있으면 push를 안내한다. (명시적 명령 시 대행)
- 변경 파일 : `git diff --name-only <기준 브랜치>...HEAD`를 작업 보고와 대조한다.
  - 생성 / 삭제한 파일과 짝인 `.meta`는 같은 파일로 본다. 생성한 파일의 `.meta`가 diff에 없으면 커밋 누락으로 보고한다.
- DoD 판정 (PR 직전 한 번) :
  - Claude 확인 항목은 `검증` 또는 `코드 확인`이면 충족, `미검증`이면 사용자에게 묻는다.
  - `(사용자 확인)` 항목은 사용자가 확인했다고 답하면 충족이다.

```markdown
**PR 작성 정보 확인** : [작업 브랜치] → [기준 브랜치]

- 연결 Issue : [#번호 / 없음]
- 변경 파일 (diff 기준) : 생성 [경로] / 수정 [경로] / 삭제 [경로]
- 작업 보고와 다른 파일 : [경로 / 없음]
- DoD :
  - Claude 확인 : [항목 - 충족 / 미충족]
  - 사용자 확인 필요 : [항목]

사용자 확인 항목을 확인하셨나요? (확인한 항목을 알려주세요)
```

## 2. 작성 규칙

| 섹션 | 규칙 |
|---|---|
| 제목 | `[말머리] 작업 내용 요약`, 명사형. Issue가 없으면 용도에 맞는 말머리 (예 : `[Feat] 플레이어 점프 기능 추가`) |
| 연결 Issue | DoD 모두 충족이면 `Closes #번호`, 아니면 `Refs #번호`. 여러 개면 한 줄에 하나. 없으면 "없음" |
| 작업 내용 | 한 항목에 변경 하나, `대상 : 변경 내용 (방법)`, 명사형 (예 : `` `PlayerJump.cs` 생성 : 스페이스바 입력 시 점프 (InputActionReference 사용) ``) |
| 확인 사항 | Claude는 직접 확인한 항목만 체크(`관계없는 파일`은 diff로 확인). 사용자 항목은 확인 답을 받은 경우만 체크하고 `(사용자 확인함)`. 해당 없는 항목은 체크하지 않고 `(해당 없음)`. 씬 소유자 항목은 팀 구성이 1인이면 `(해당 없음)` |
| 화면 | 눈으로 볼 동작이면 이미지 / 영상, 아니면 "불필요" |
| 참고사항 | 리뷰 시 중요한 파일 경로 |
| 특이사항 | 전달·우려 사항, 없으면 "없음" |

양식 :

```markdown
## 연결 Issue
- 

## 작업 내용
- 

## 확인 사항
- [ ] Unity에서 실행 테스트해 보았다.
- [ ] 콘솔에 에러가 없다.
- [ ] 관계없는 파일이 같이 들어가지 않았다.
- [ ] 씬 파일이 들어갔다면 내가 그 씬의 소유자이다.
- [ ] 연결된 Issue의 완료조건(DoD)을 모두 충족했다.

## 화면
- 

## 참고사항
- 

## 특이사항
- 
```

## 3. 생성 전 승인

요약만 보여 주고, "전문" 요청 시 본문 전체를 보여 준다. 승인 없이 생성하지 않는다.

```markdown
**PR 생성 확인**

| 항목 | 내용 |
|---|---|
| 제목 | |
| 브랜치 | [작업] → [기준] |
| 연결 Issue | [Closes #번호 / Refs #번호 / 없음] |
| 작업 내용 | [n개] |
| 체크하지 않은 확인 사항 | [항목 / 없음] |

생성할까요? (전문 확인 시 "전문")
```

## 4. 생성

- `gh pr create --base <기준 브랜치> --head <작업 브랜치> --title "<제목>" --body-file -`

```markdown
**PR 생성 완료** : #[번호] [제목]

- 링크 : [URL]
- 체크하지 않은 확인 사항 : [항목 / 없음]

다음 단계 : 병합 (사용자, 명시적 명령 시 Claude 대행)
```

## 5. 병합 · Issue Close (명시적 명령 시 대행)

- `gh pr merge --<병합 방식> --delete-branch`. 병합 승인이 브랜치 삭제 승인을 겸한다.
- 병합 뒤 `git branch --show-current`, `git branch --list <작업 브랜치>`로 확인하고 남은 정리만 한다. (기준 브랜치로 `switch`, `pull --ff-only`, 남은 로컬 브랜치 삭제)
- `Closes`로 연결한 Issue는 GitHub 기본 브랜치에 병합되면 자동으로 닫힌다. 기준 브랜치가 기본 브랜치가 아니면 `gh issue close`를 안내한다.
- `Refs`로 연결한 Issue는 미충족 DoD를 별도 Issue로 등록할지 묻고, Close는 사용자가 정한다.
- Develop을 쓰는 경우 Develop → main 릴리스 PR은 사용자가 하며 `merge` 방식을 권장한다.
